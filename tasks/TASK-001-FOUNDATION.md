# Phase 0 — Mandatory Baseline Audit

## Rule

**Do not make architectural or business-feature changes until this audit is complete.**

Inspect the existing solution/project and report the result.

### A. Repository and solution placement

Verify:

```text
Faed/
├── Faed.sln / Faed.slnx
├── src/
│   └── Faed.Web/
├── tests/            # may not exist yet
├── AGENTS.md
├── CLAUDE.md
├── docs/
├── tasks/
└── .claude/
```

If Visual Studio generated a redundant nested structure such as:

```text
Faed/Faed/Faed.Web
```

or the repository root is not the solution root, report it.

Do not silently normalize a badly created repository structure without explaining the change.

### B. Project identity

Verify that the existing web project is:

- named `Faed.Web`;
- an ASP.NET Core MVC project;
- targeting `.NET 10`;
- nullable enabled;
- using Razor Views;
- using the expected SDK/project format.

### C. Visual Studio template baseline

Verify that the generated template contains the expected baseline pieces, including where applicable:

- `Program.cs`;
- `Controllers/HomeController.cs`;
- `Views/`;
- `wwwroot/`;
- `appsettings.json`;
- development configuration;
- `Properties/launchSettings.json`;
- Bootstrap/static assets supplied by the template;
- HTTPS development launch profile.

Do not remove working template files merely for cosmetic reasons during this phase.

### D. Identity baseline

Verify that **Individual Accounts / ASP.NET Core Identity** was actually selected and generated correctly.

Confirm:

- Identity services are registered;
- authentication middleware is configured correctly;
- an Identity DbContext exists;
- the generated Identity UI/Razor Class Library integration is wired correctly;
- Register and Login routes/pages are available;
- authentication works after schema creation;
- no custom full Identity scaffold has been generated unless the developer intentionally created one.

If the project was accidentally created with `Authentication: None`, treat this as a **blocking baseline error**.

### E. Database/provider audit

Identify the database provider generated by Visual Studio.

The final Faed architecture requires:

- EF Core;
- SQL Server;
- SQL Server LocalDB for local Windows development where appropriate;
- migrations owned by Infrastructure after the foundation refactor;
- no secrets committed.

If the template generated SQLite or another provider, do **not** call the baseline "wrong" merely because the template chose it.

Instead:
1. report what Visual Studio generated;
2. confirm Identity works as a template baseline;
3. migrate the project deliberately to SQL Server as part of the foundation work;
4. document the change.

### F. Build and run baseline

Before restructuring:

- run restore;
- run build;
- start the generated web app;
- verify Home renders;
- verify Register/Login UI is reachable;
- record any warnings/errors.

### G. Git safety baseline

Before modifying architecture:

- inspect `git status`;
- confirm generated source files that belong in Git are not accidentally ignored;
- confirm secrets/local artifacts are ignored;
- do not overwrite unrelated uncommitted developer changes.

---

## Baseline audit outcome

Classify the result as one of:

### `PASS`
The Visual Studio baseline is correct enough to adopt.

Proceed to Phase 1.

### `PASS WITH SAFE CORRECTIONS`
The project is fundamentally correct but needs expected foundation corrections such as changing the EF provider to SQL Server.

Report the corrections, then proceed.

### `BLOCKED`
Stop before continuing if there is a fundamental setup problem such as:

- wrong project template;
- wrong target framework;
- `Faed.Web` missing;
- Identity was not selected;
- broken solution structure that could cause destructive movement;
- baseline cannot build for reasons unrelated to the intended architecture work.

When blocked:
- explain exactly what is wrong;
- propose the smallest correction;
- do not create marketplace features;
- do not recreate the whole project unless explicitly requested.

# Phase 2 — Complete the Solution Structure

The target solution is:

```text
Faed.sln / Faed.slnx

src/
├── Faed.Domain/
├── Faed.Application/
├── Faed.Infrastructure/
└── Faed.Web/

tests/
├── Faed.UnitTests/
└── Faed.IntegrationTests/
```

Create only the missing projects.

Configure references exactly as documented:

```text
Domain
↑
Application
↑
Infrastructure

Web → Application + Infrastructure
```

More precisely:

- `Faed.Domain`: no project dependency;
- `Faed.Application` → `Faed.Domain`;
- `Faed.Infrastructure` → `Faed.Application` + `Faed.Domain`;
- `Faed.Web` → `Faed.Application` + `Faed.Infrastructure`.

Tests reference only what they genuinely test.

# Phase 3 — Identity and Persistence Foundation

## Identity

Preserve the working Visual Studio-generated Identity baseline while adapting it to the documented architecture.

Create/extend `ApplicationUser` only with fields genuinely required now:

- `CreatedAtUtc`
- `IsActive`

Do not create `MerchantProfile` yet.

Roles:

- `Buyer`
- `Merchant`
- `Admin`

Seed roles idempotently.

Merchant verification remains a separate future domain state.

## Persistence

The final foundation must use:

- EF Core;
- SQL Server;
- one application DbContext in Infrastructure;
- Identity sharing that DbContext where practical;
- migrations in Infrastructure;
- no committed credentials.

If moving the Visual Studio-generated DbContext from Web to Infrastructure:

1. preserve Identity behavior;
2. update namespace/project references deliberately;
3. recreate or move migrations only when technically correct;
4. do not leave duplicate DbContexts or competing Identity stores;
5. prove registration/login still works afterward.

Use user secrets/environment variables for sensitive development configuration.

A non-secret LocalDB development connection string may be documented, but credentials must never be committed.
