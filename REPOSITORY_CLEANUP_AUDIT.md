## C. Key finding that changes the master plan's default removal list

`tasks/FAED_FINALIZATION_MASTER_PLAN.md` lists `AGENTS.md` and (implicitly, via "historical
UI/implementation plans") parts of `docs/` as removal candidates, and `TASK-019`'s own
required-cleanup list repeats `AGENTS.md`, `CLAUDE.md`, `.claude/`,
`.github/copilot-instructions.md`, `START_PROMPT.md` verbatim. Decision #5 in the tracker
says the same. **Before this audit, that removal list was untested against the actual
codebase.** It is not safe to apply as-is for two specific files:

| File | Times referenced elsewhere in tracked repo | Times referenced *inside `src/Faed.Web/**/*.cs` and `*.cshtml` code comments* |
|---|---|---|
| `AGENTS.md` | 69 files | **64 occurrences across ~50 source files** — cited as design rationale, e.g. `Listing.cs:14` `<see cref="ListingVariant"/> (AGENTS.md Rule A, docs/adr/0002)`, `InventoryService.cs:250` `// stock must never move without the record of why (AGENTS.md §7)` |
| `docs/*` (all numbers combined) | 245 files | **564 occurrences across ~150 source files** — nearly every entity, service, and configuration class cites a specific `docs/0X-...md §N` as the reason a rule exists |

The Definition of Done in the master plan (#10) requires **"no stale references to deleted
tests/agents/skills remain."** Deleting `AGENTS.md` and the `docs/00`–`docs/20` spec files
(PRD, business rules, domain model, architecture, security, test strategy, acceptance
criteria, etc.) as a blanket action would immediately create 600+ dangling comment
references throughout the shipped application code — the opposite of the "no stale
references" goal, and a large, error-prone rewrite if attempted (hundreds of individual
comment edits, high chance of introducing typos/inconsistencies for a student submission).

**This audit recommends splitting "agent/skill/task-development files" into two groups
instead of removing them as one block:**

1. **Process/orchestration files that exist only to run Claude/Codex sessions** — safe to
   remove; nothing in `src/` or `tests/` references them.
2. **The engineering-contract/spec files (`AGENTS.md`, `docs/00`–`docs/20`,
   `docs/adr/*`)** — these are exactly the files `docs/00-SPEC-MAP.md` itself defines as the
   "read map" (the spec map's own table stops at `docs/20`; `docs/21`–`docs/25` are not in
   it). They are cited pervasively as the *rationale* for non-obvious business rules in the
   shipped code, per `docs/00-SPEC-MAP.md`'s own rule ("Reference the relevant
   specification/ADR when a non-obvious rule needs explanation"). Removing them breaks that
   contract. Recommendation: **KEEP** `AGENTS.md` and `docs/00`–`20` + `docs/adr/*` in the
   final submission. This does not contradict "don't mention Claude/Codex/agents in the
   README" (TASK-020) — the README simply would not link to `AGENTS.md`; the file can still
   exist in the repo as the project's engineering/business-rules reference, the same way a
   real engineering team keeps a design doc without advertising it on the landing page.
   `CLAUDE.md` is different: it is Claude-Code-specific routing (4 references, 0 in
   `src/`/`tests/`) and can be removed cheaply.

This is flagged here, not resolved unilaterally, per `AGENTS.md` §2's own instruction to
flag a conflict before changing an authoritative rule. **TASK-019 should treat the KEEP
recommendation for `AGENTS.md`/`docs/00-20`/`docs/adr/*` as the default unless the user
overrides it when approving this audit.**
